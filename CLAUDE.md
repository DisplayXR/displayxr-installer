# CLAUDE.md

Project guidance for Claude Code (claude.ai/code) when working in this repo.

## What this repo is

`displayxr-installer` produces the **end-user meta-installer** for DisplayXR — one `.exe` / `.pkg` per OS that chains the component installers (runtime + Leia plug-in + Leia conversion (gated, below) + MCP Tools + Open Conversion provider + demos) into a single guided flow. **The DisplayXR Shell is not a bundle component on any platform** (David, 2026-11-28): it is the catalog add-on `displayxr-shell`, installed from the Dashboard or its own installer; `shell` stays a `versions.json` pin and is listed in `$IntentionallyUnbundled`.

Tracks issue [`DisplayXR/displayxr-runtime#284`](https://github.com/DisplayXR/displayxr-runtime/issues/284).

**Not in this repo:**
- The per-component installers — each component publishes its own installer to its own GitHub Release. This repo only assembles them.
- The dev-orchestrator scripts (`scripts/setup-displayxr.{sh,bat}`) — those live in `DisplayXR/displayxr-runtime`. The bundle is the *user-facing* counterpart to the dev orchestrator.

## Issue tracking

All issues for this work live on `DisplayXR/displayxr-runtime` (issue numbers like `#284`). This repo does not maintain its own issue tracker. Commit subjects: `<type>(#NN): <subject>`.

## Cross-repo dependencies

| Source repo | What we consume | How |
|---|---|---|
| `DisplayXR/displayxr-runtime` | `scripts/lib/components.sh` (per-component asset table) | `curl https://raw.githubusercontent.com/.../$RUNTIME_TAG/scripts/lib/components.sh` |
| `DisplayXR/displayxr-runtime` | `DisplayXR-Installer-*.pkg` (macOS), `DisplayXRSetup-*.exe` (Windows) | `gh release download $RUNTIME_TAG --repo ...` |
| `DisplayXR/displayxr-leia-plugin` | `DisplayXRLeiaSRSetup-*.exe` (Windows) | `gh release download $LEIA_TAG --repo ...` |
| `DisplayXR/displayxr-mcp` | `DisplayXRMCPSetup-*.exe` (Windows), `DisplayXRMCP-*.pkg` (macOS) | `gh release download $MCP_TAG --repo ...` |
| `DisplayXR/displayxr-leia-conversion` | `DisplayXRLeiaConversionSetup-*.exe` (Windows), `displayxr-leia-conversion_*_amd64.deb` (Linux) — **only when `leia_plugin` ≥ v2.24.0** | `gh release download $LEIACONV_TAG --repo ...` |

Components without a macOS `.pkg` today (Leia, the conversion providers) are silently skipped on the macOS side. A component that HAS a `.pkg` also needs an `extract_<name>` rule in `build-bundle.sh`, or it is downloaded and skipped with a WARN (how MCP stayed out until 2026-11-28). The bundle build picks them up automatically when their releases start carrying `.pkg` artifacts and the runtime repo's `components.sh` populates `COMPONENT_PKG_MACOS_<name>`.

## Build commands

```bash
# macOS
./scripts/build-bundle.sh --version v0.1.0
# → _out/DisplayXRBundle-0.1.0.pkg

# Windows (from non-elevated cmd; the bundle itself elevates at install time)
scripts\build-bundle.bat --version v0.1.0
:: → _out\DisplayXRBundle-0.1.0.exe
```

Prerequisites:
- **macOS:** `gh` (with auth), `jq`, `productbuild`, `pkgutil` (Xcode CLT)
- **Windows:** `gh` (with auth), NSIS 3.x (`choco install nsis`), PowerShell, 7-Zip (`7z`: takes `dxr-get.exe` out of the runtime installer; preinstalled on GitHub's Windows images)

## Release flow

`workflow_dispatch` on `.github/workflows/publish-bundle.yml` — release engineer triggers manually with a tag input (e.g. `v0.1.0`). Workflow:
1. Builds macOS `.pkg` and Windows `.exe` in parallel
2. Creates GitHub Release with the input tag
3. Attaches both artifacts via `softprops/action-gh-release@v2`

**Not** auto-fired on component releases (would re-publish untested bundles).

## versions.json — auto-mirrored, do not hand-edit

`versions.json` in this repo is **mirrored byte-for-byte from
[`DisplayXR/displayxr-runtime/versions.json`](https://github.com/DisplayXR/displayxr-runtime/blob/main/versions.json)**
by the runtime's `.github/workflows/versions-bump.yml` and its
`BumpVersionsJsonOnTag` job. When a sibling component (runtime,
shell, leia plug-in, mcp, demo) tags a release, the runtime updates
its `versions.json` and pushes the same content here in the same
workflow run. No human PR needed.

**Do not hand-edit `versions.json` in this repo.** The first step of
`publish-bundle.yml` (`assert-versions-in-sync`) downloads
`displayxr-runtime/main/versions.json` and diffs it against the
local file; any drift fails the bundle build before anything is
compiled. If the mirror commit ever silently fails on the runtime
side, the right recovery is to re-run the runtime's
`versions-bump.yml` (via `workflow_dispatch`) — never to edit this
file directly.

Schema: flat top-level keys matching the asset-table identifiers in
[runtime's `scripts/lib/components.sh`](https://github.com/DisplayXR/displayxr-runtime/blob/main/scripts/lib/components.sh)
(`runtime`, `shell`, `leia_plugin`, `mcp_tools`, `gauss_demo`, …).

**A pin is not a bundle component.** `scripts/check_bundle_coverage.ps1` fails on any
`versions.json` key that is neither chained by both build scripts nor named in its
`$IntentionallyUnbundled` table (with the reason). A key for a component that has no release
yet is listed there **before** its first release: the runtime adds such a key to `versions.json`
on that first release and mirrors it here in the same run (`leia_conversion`, `ultraleap`).
Where the bundle is going (a core bundle that downloads catalog components, plus an offline
full bundle): `displayxr-runtime/docs/roadmap/catalog-driven-bundle.md`.

**`leia_conversion` is conditionally bundled — the one pin whose state depends on another pin.**
The Leia SR plug-in carried the conversion provider up to 2.23.x; from 2.24.0 it does not and the
provider ships only as the `leia_conversion` component. The rule (one version, three copies:
`scripts/leia_conversion_gate.ps1`, `scripts/lib/leia-conversion-gate.sh`, `LEIACONV_MIN_LEIA_VER`
in the `.nsi`; the coverage check fails when they differ):

| `leia_plugin` pin | `leia_conversion` | Enforced by |
|---|---|---|
| < v2.24.0 | must NOT be chained: the old plug-in installer takes the provider registration back (Windows), and the component's `.deb` declares `Breaks`/`Replaces` against it (Linux) | build scripts skip it; the `.nsi` has an `!error`, `build-bundle-linux.sh` exits 1 if it is chained anyway; coverage check reports it as skipped |
| ≥ v2.24.0 | MUST be chained, or a display that had conversion loses it on upgrade | build scripts download + chain it and fail without it; coverage check treats it like every other component |

The flip happens through a `versions.json` mirror commit that no PR here reviews, so the coverage
check verifies the wiring in **both** states. Things that are load-bearing:

- **Windows order:** the `Leia conversion` section is declared after `Leia SR plug-in` and must
  stay there (the plug-in installer removes its leftover provider copy, then the component writes
  its own registration). The section also re-runs the component installer when it is installed and
  current but not the *registered* provider — a version compare alone would skip it.
- **Sub-choice:** `.onSelChange` keeps it unticked whenever the plug-in is unticked.
- **Linux:** `install.sh` hands every `.deb` to ONE `apt-get install`; do not turn that into a
  loop, or apt refuses the component over an installed older plug-in.
- **User-facing text** says "Leia conversion" and "the Leia conversion runtime"; the vendor's
  technology name stays out of the installer UI and the Linux bundle's scripts (coverage check).
- The bundle never installs the vendor's conversion runtime. macOS has no build of the component.

Full design rationale:
[`displayxr-runtime/docs/specs/runtime/versions-json-autobump.md`](https://github.com/DisplayXR/displayxr-runtime/blob/main/docs/specs/runtime/versions-json-autobump.md).

**Windows Leia SR rows are detection-gated (David, 2026-11-28).** `SecLeia` / `SecLeiaConv` are `Section /o`. `.onInit` ticks them only when installed, on `/LEIASR=1`, or when `dxr-get detect` (the signed catalog's rules) reports a **high**-confidence Leia SR display; `low`, offline and any failure leave them unticked. The bundle embeds the `dxr-get.exe` of the runtime installer it chains (`build-bundle.bat`, 7-Zip) because no runtime may be installed yet at `.onInit`; `installer/windows/detect-display.ps1` runs it with a bounded wait and parses the JSON (NSIS strings would truncate it). Load-bearing: "installed => ticked" must stay, or an installed plug-in is **removed** by its section's unticked branch. Linux has no POSIX `dxr-get` yet, so the Linux bundle still installs the plug-in unconditionally (it is inert without the display maker's runtime).

## Things to be careful about

- **Don't strip ad-hoc signatures** from macOS dylibs when re-wrapping the runtime `.pkg`. `pkgutil --expand` / `pkgutil --flatten` preserve signatures by default; do NOT add `install_name_tool` or `codesign --remove-signature` to the build flow. Regression of `DisplayXR/displayxr-runtime#279` would SIGKILL the installed runtime at `dlopen`. The build script verifies the runtime payload's presence after re-wrap; extend that check if you change the rewrap flow.
- **Don't auto-fire `publish-bundle.yml`.** It's `workflow_dispatch` for a reason (compat-test gate). The `assert-versions-in-sync` job exists to *fail-fast* on drift, not to repair pins.
- **Don't sign anything.** v1 ships unsigned (#280 / #281 in runtime repo are parallel work). When those land, signing gets a small CI block; until then, no `codesign` / `signtool` calls.
- **Exception: the Android installer APK is release-signed, with ONE key, forever.** `DisplayXR-Installer-<ver>.apk` is signed in CI with the key in the GitHub environment `android-installer-release` (main-only), and every publish path refuses an APK whose signer is not the pin in `android-installer/release-signing-cert.sha256` (`android-installer/scripts/verify-release-signature.sh`). Never "fix" a failing release by editing the pin or falling back to the debug key: a different key cannot update the copies already on tablets. Design, rotation and backup: `android-installer/README.md` § *Signing*.
